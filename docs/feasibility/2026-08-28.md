2. Call the guide and read revision 0.
3. Rename the tool through native WebMCP; observe `search_catalog_native` at revision 1 in the UI.
4. Click **Add wait step** through the UI; read the added node natively at revision 2.
5. Attempt a native write against revision 1; receive `revision_conflict`; the visible draft is unchanged.
6. Insert a second wait node natively at revision 3. Click **Undo last edit**; a native read sees revision 4 with only the earlier UI-added wait node.
7. Attempt an invalid tool name; receive `invalid_value`; the visible draft is unchanged.
8. Click **Revoke agent draft edits**; a native edit against the current revision receives `agent_edits_revoked`. The guide reports the blocker and the correct next step.
9. Open the uninstrumented target and fetch its native inventory: **No WebMCP tools are available in this document.**

The revocation check covers the fixture's draft-edit permission only. It does not prove extension permissions, selected-tab scope, registration removal, or in-flight cancellation. The target's tab marker is synthetic test data, not evidence of a shared authenticated session.

## Actual runtime checks performed here

The second fixture imports the repository's `ContentRuntime` and `createMainWorldRuntime`. It uses the real DOM scanner, Capability Graph/compiler, tokenized `window.postMessage` bridge, argument validation, and DOM executor. Exporting the existing content class makes it available to this fixture without changing the extension's automatic startup. No tool handler or executor is called directly by the testing agent.

1. The scanner discovered the visible product-search form. Native inventory exposed `search_products` with the inferred `q` and `category` schema.
2. A native call populated the form and submitted it once. The returned result reported `completed`, and the visible search result and submission counter agreed.
3. An invalid category returned `invalid_arguments` without changing either field, the result, or the counter.
4. Before the fix, disabling prevented execution (`permission_blocked`) but left the tool registered: the runtime expected a removal method that this host does not expose.
5. After the fix, disabling removed the tool from the agent's native inventory. Calling the old handle returned a stale-registration error without submitting the form.
6. Re-enabling restored the tool. A freshly fetched native handle submitted a second search successfully. An additional attempt through a retained REPL helper also returned a stale-registration error; it did not execute. The raw evidence preserves that attempt and the successful retry.

The fix supplies a registration-specific `AbortSignal`, as described in the [Chrome imperative API guide](https://developer.chrome.com/docs/ai/webmcp/imperative-api), and verifies removal against readable host inventory. It retains explicit legacy removal methods and reports failure conservatively when safe removal cannot be established. Four added unit cases cover the native lifecycle, ignored signals with and without a legacy removal method, and unavailable inventory.

This proves useful runtime components against a real native consumer. It does **not** prove extension installation/injection, cross-world messaging, selected-tab pairing, the canonical Studio config, an authenticated session, or cancellation of work already in flight. G1–G3 remain open.

## Parallel verification follow-up

Three independent reviews covered runtime correctness, evidence accuracy, and the remaining browser boundary. They found no unsupported feasibility claim or change to settled decisions. The code review findings led to these fixes:

- **Removal recovery:** an abort can remove a tool even if the following inventory read fails. The runtime now resolves that uncertain registration when readable inventory returns, so re-enabling can register the tool again.
- **Inventory safety:** unsupported inventory shapes no longer count as verified emptiness. Removal checks retain exact tool names, and the bulk-clear fallback does not discard a separately named page-owned tool or run after a failed inventory read.
- **Inspector tab routing:** the worker now includes the originating tab ID from Chrome's sender metadata. The inspector rejects unscoped or mismatched updates and prioritizes actual sender metadata over a claimed payload ID. This fixes the reproduced case where tab B's state overwrote inspector A while its commands still targeted A.

The follow-up adds 17 unit cases: nine runtime cases and eight inspector/worker routing cases, bringing the suite to **94 tests across 14 files**. The inventory failure cases use mocked hosts, and routing tests use mocked Chrome messaging. They are regression evidence, not native browser or installed-extension proof.

A fresh native browser run against the combined changes returned two successful searches and one invalid-input rejection. After disabling, the native inventory was empty and an old handle was rejected before execution. Re-enabling and fetching a new handle restored execution. See the [new native evidence](native-runtime-reviewed-2026-08-28.json).

The initial runtime evidence remains historical: its captured events, hashes, and 77-test checkpoint have not been rewritten to describe later code. Its source-snapshot metadata identifies the base commit and the [preserved patch](native-runtime-initial.patch) needed to reconstruct the initial runtime and test files. Reconstruction was checked against the original hashes.

## Reproduce the native fixture

From the repository root:

```sh
npm install --no-package-lock --ignore-scripts
npm run build
npm test
npm run spike:native
```

Dependency ranges and the absence of a lockfile mean this recipe starts a fresh verification run, not an exact historical dependency installation. Compare installed versions with the environment record above. The historical source snapshot and hashes are retained separately.

Open `http://127.0.0.1:4174/` in the supported native browser. Ask the agent to use the listed native Studio tools and follow the checks above. Use the normal UI for the UI steps. The page displays its API status, revision, draft, and call log. Reload starts a new experiment. In an unsupported browser it reports the missing API and installs no fallback.

`http://127.0.0.1:4174/target.html` is the clean target for the next extension experiment. It registers no page tools and uses no mocked model context. Do not use `demo/site/assets/shared.js` for native evidence: that existing demo replaces the API with a mock.

The source is in [spikes/native-webmcp](../../spikes/native-webmcp/). The server binds only to loopback and serves an explicit list of fixture assets; it does not expose the repository or provide a relay. `WEBMCP_SPIKE_PORT` can change the port.

### Reproduce the actual runtime fixture

With the same dependencies installed, run:

```sh
node spikes/native-runtime/serve.mjs
```

Open `http://127.0.0.1:4175/` in the supported native browser. Discover and invoke `search_products` with `{"q":"keyboard","category":"keyboards"}`. Confirm the visible result and submission count. Test an invalid category, then use **Disable inferred tools** and check that native inventory is empty. Use **Enable inferred tools**, fetch a new native handle, and invoke again. Use **Refresh diagnostics** to inspect the actual runtime result. Reload resets the experiment.

The [runtime fixture](../../spikes/native-runtime/) bundles the actual TypeScript modules on request. Its loopback server serves only the fixture, stylesheet, and bundle; it provides no relay or browser-control endpoint.
