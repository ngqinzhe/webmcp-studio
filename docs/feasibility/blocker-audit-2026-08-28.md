### Browser support is still split across environments

Current [OpenAI Site tools documentation](https://learn.chatgpt.com/docs/webmcp) establishes native consumption in the desktop built-in browser. The [Chrome extension guide](https://learn.chatgpt.com/docs/chrome-extension) establishes tab control and side chat, without establishing native Site tools through that connection. The [built-in browser guide](https://learn.chatgpt.com/docs/browser) describes a separate profile; the inspected documentation does not provide a supported third-party MV3 installation path there.

The candidate remains one Chrome profile containing both extensions, Studio, and the selected target. Its native ChatGPT capability needs evidence. The current failure concerns the tested connector, not every possible ChatGPT setup. A new chat, an inspector invocation, or a direct JavaScript call is not proof that the missing native route works.

Chrome provides [webpage-to-extension messaging](https://developer.chrome.com/docs/extensions/develop/concepts/messaging) and [page/content-script communication](https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts#communication_with_the_embedding_page). Those are useful same-browser building blocks; they do not establish communication across separate browser profiles.

## 2. Reproduced defects

Run the dated, synthetic [audit probes](../../spikes/blocker-audit/check.mjs):

```bash
node spikes/blocker-audit/check.mjs
```

At the audited baseline this exits **1**, intentionally, because unsafe behavior is observable. Its captured output is in the machine record. It bundles the real source in memory but uses mocked Chrome transport, a synthetic jsdom page, and a mocked server filesystem. It is not a native-browser test or a complete security suite.

### Uncertain action delivery can be replayed

[routeCommand](../../extension/service-worker/service-worker.ts#L147) retries a failed message after injecting the runtime, regardless of command type or whether the first action already took effect.

The mock performed a counted action, then rejected its reply. Reinjection succeeded; the retry remained actionable. The observed count was **2**, followed by final success. No real transaction occurred.

**Required correction:** separate connection recovery from action retry. An ambiguous action result must stop or be reconciled; it must not be automatically replayed. Add a regression for “effect happened, reply lost”, including navigation/timeout cases. A request ID helps only if deduplication survives the relevant failure.

### An explicit read exposes a password value

[readTargetResult](../../core/execution/execute.ts#L971) returns input values, while [executeRead](../../core/execution/execute.ts#L1004) checks visibility without checking sensitivity.

A deliberately configured read of a synthetic password input returned its sentinel unchanged with a successful result. **This does not demonstrate automatic scanner extraction, native exfiltration, or access to any real password.**

**Required correction:** block sensitive reads and sanitize observations, results, and traces; pause observation during human login. Test passwords, tokens, hidden credentials, and account transitions with synthetic data before authenticated use.

### Development-server defects

The [demo server](../../scripts/serve-demo.mjs#L15) decodes a request path outside its error handler and tests containment with a string prefix.

The source-level probe observed an uncaught URIError for malformed encoding. An encoded traversal toward a sibling directory named “site-audit” also reached the mocked file reader, because that directory shares the “site” prefix. No sibling file or actual outside-root read was created.

These findings concern the loopback mock-demo server, not the separate native fixture servers. Fix malformed-path handling and directory containment before reusing it beyond that role. They do not establish a WebMCP architecture failure.

### Domain access is not simply “localhost only”

Static automatic injection is limited to loopback. The current **activeTab + scripting** permissions and explicit toolbar action can programmatically inject into an eligible ordinary public tab. The temporary grant persists across same-origin navigation and ends on cross-origin navigation or tab closure. [activeTab](https://developer.chrome.com/docs/extensions/develop/concepts/activeTab), [scripting](https://developer.chrome.com/docs/extensions/reference/api/scripting)

Entering a domain or importing JSON grants nothing. Persistent domain activation and its permission UI are unbuilt; the current manifest has no optional host declarations, and its update listener only clears cached state. Any extra permission needs human review. [Optional permissions](https://developer.chrome.com/docs/extensions/reference/api/permissions)

### Target pages have compatibility conditions

Check the final origin, effective secure-context status, origin-keyed agent cluster, enforced/inherited “tools” policy, frame boundaries, and actual packaged-adapter registration. The draft exposes WebMCP in secure contexts and specifies denial for non-origin-keyed clusters or denied tools policy. Origin-keying is distinct from COOP/COEP cross-origin isolation. [WebMCP draft](https://webmachinelearning.github.io/webmcp/), [Chrome prerequisites](https://developer.chrome.com/docs/ai/webmcp), [origin-keying](https://web.dev/articles/origin-agent-cluster)

The default tools policy is “self”; explicit denial can still prevent registration. Chrome documents delegated iframe tools, while the current built-in ChatGPT consumer does not discover iframe registrations. A top-level wrapper would need its own authorized execution path. [Policy](https://webmachinelearning.github.io/webmcp/#permissions-policy-integration), [Chrome iframe support](https://developer.chrome.com/docs/ai/webmcp/imperative-api#cross-origin-iframes), [ChatGPT limitations](https://learn.chatgpt.com/docs/webmcp#limitations)

Injection permission does not establish an exemption from these document restrictions, and MAIN-world code is subject to the page CSP. Exact negative-policy behavior in installed Chrome remains unmeasured. Test allowed/denied policy, non-origin-keyed, and relevant frame cases on controlled fixtures; treat an incompatible target as unsupported without altering its restrictions. [Content-script policy](https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts)

## 5. Recommended order

1. **Resolve native consumption first.** Use the existing fixture in the chosen ChatGPT/Chrome setup; our extension need not be installed for this initial probe. If native tools are unavailable, stop that route and obtain platform clarification or an explicit design decision.
2. **Confirm judging setup in parallel.** Ask whether judges can install our extension, how it must be distributed, and which browser/profile they will use.
3. **With explicit installation permission, test the packaged extension.** Prove injection and native consumption on the clean target. Then prove the minimal scoped Studio connection in that same setup before relying on it for full discovery.
4. **Fix the safety defects and build the missing controls using synthetic state.** Keep real accounts and consequential actions out until those checks pass.
5. **Build one complete canonical flow and reproduce it independently.** This closes the remaining product integration questions; it does not remove the agreed MVP scope. Settle public-source/license, deployment, media, eligibility, and conditional Reddit access before submission.

The runtime code is unchanged by this audit. Prior native evidence and the 94-test baseline are retained, not presented as fresh full-suite results. The new diagnostic was executed and its source/output recorded. The audit identifies known blockers and explicit unverified boundaries; it cannot guarantee that future implementation or an untested target will reveal no additional issues.
